Pipelines that lie

A data pipeline can show all green while it is silently wrong. I have come to think this is the normal failure, not the rare one. Loud failures get fixed. Quiet ones get trusted.

None of this is new. Many people have written about it. I am writing it down because I find it useful to name the patterns plainly. Each example below is an invented example, not a real system.

My thesis is short. Engineering for trust means making failure loud, honest and testable.

Six ways a green pipeline lies

1. The success check that looks for the word "error".

Say a job writes a log, and a wrapper decides success by searching the log for "error". The job then hits "Access denied" when it reads its input. The word "error" never appears. The wrapper sees none, and reports success. The check was built around one failure phrase, and the world had another.

2. The job that has never run.

Say a scheduled job was set up, but its trigger was never enabled. Nothing ran. The dashboard shows the last status as success, because the last status is empty and empty is read as fine. Silence looks the same as health.

3. The stage that drops rows and still exits 0.

Say a parsing stage reads a file and skips any row it cannot parse. It logs a warning and carries on. At the end it exits with code zero (a number a program returns when it ends; 0 means no crash). Half the rows may be gone. The exit code only said the program did not crash.

4. Retries that never run.

Say a job may retry only within one hour of its first attempt. The first attempt hangs for the full hour, then fails. The retry window has already closed, so no retry happens. The setting exists. The protection does not.

5. Counting a file as processed after a failed transaction.

Say a loader writes rows to a database inside a transaction (a group of writes that all succeed or all get undone). The loader marks the file as done before the commit, and the marker is stored outside the transaction. The commit then fails and the rows are undone, but the marker stays. The file is now counted as processed and will never be picked up again.

6. The workflow that reports success after a failure.

Say a workflow has three steps, and step two fails. Step three is set to run "always", to clean up. The workflow's final status is taken from the last step. Cleanup succeeds, so the whole run is green.

These six look different. They share one cause. Each check measured something nearby instead of the thing that matters.

What I do about it

Fail closed.

If a check cannot tell whether things went well, it should say they did not. Unknown is not success. A missing log, an empty status, an unreadable result: all of these should stop the line, not wave it through. The cost is a few false alarms. I will take that trade.

Count rows in and out.

Every stage should know how many records came in and how many went out, and it should account for the difference. Some rows are dropped on purpose, and that is fine, if the count says so. A stage that cannot explain its own difference has not finished.

Plant a known failure and prove the check catches it.

A check that has never failed has never been shown to work. So I put a deliberate fault into a self-test: a file the job cannot read, a row that cannot parse, a step that is forced to fail. Then I confirm the pipeline goes red. If it stays green, I have found a lying check before it found me. This is the single most useful habit on the list. The same goes for AI-written code. A review step that cannot reject anything is worth nothing.

Record what each run actually used.

For every run, write down the inputs it read, the version of the code, the settings, and the time. Not what was meant to be used. What was used. When a result looks odd later, that record turns a guess into a lookup.

Label confidence: proven, inferred, unknown.

When I report on a pipeline, I tag each claim. Proven means I saw it happen, with evidence. Inferred means it follows from something I saw, but I did not see it directly. Unknown means I have not checked. Most bad status reports mix these three into one confident voice. Keeping them apart is a small habit that prevents big surprises.

Separate "the job ran" from "the result is right".

These are two questions with two answers. The first is about execution. The second is about the output. A green tick can honestly answer the first. Only a check on the output can answer the second. Use row counts, value ranges, and totals that must match. Add a sample that a person looks at. I report the two answers side by side, never merged into one light.

Questions to ask of any pipeline

  • What does "success" actually test? Execution, or output?
  • What happens if the check itself cannot run? Does it fail closed?
  • Has this check ever been seen to fail, on purpose, in a test?
  • How many records went in, how many came out, and where is the difference explained?
  • If a retry is configured, can it really fire? What does it count from?
  • Is "done" recorded in the same transaction as the work it describes?
  • If one step fails, can a later step overwrite the final status?
  • Has every scheduled job run at least once, and how do I know?
  • What did the last run actually use, and where is that written down?
  • Which of my claims about this pipeline are proven, which inferred, which unknown?

A pipeline you trust should be one that has had the chance to fail in front of you, and did, loudly. If it has never been asked to fail, you do not know yet whether it can.
